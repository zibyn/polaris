# 密码登录开关从三档改为两档

`settings.password_login` 由「关闭 / 仅管理员(默认) / 所有 User」改成「关闭 / 开启」,默认**开启**。理由有三:一是「仅管理员」这档判断的是调用者有没有 Management API Role,而那个 Role 的含义是"能不能调管理接口",和"能不能用密码登录"是两件事,把两者绑在一起是模型错位;二是默认开启在新实例上**效果等同原来的「仅管理员」**,因为密码从不随注册发放(`authentication.md`:注册时从不要求),普通用户根本没有密码可用;三是三档让"密码登录开着没开着"变成需要对着角色表推断的问题。

## Considered Options

- **保留三档,只补自己锁死自己的守卫**:diff 最小,但把错位的模型留在原地。
- **砍成两档但默认「关闭」**:安全默认,却把 ADR 0006 要解决的问题搬回来——全新实例必须先配通道或 Provider 才能进管理端。
- **只把「仅管理员」改名或改语义**:不解决"能用密码"和"有角色"耦合这件事。

## Consequences

- **存量迁移必须把 `'admins'` 折成 `'on'`,不能折成 `'off'`**:折成 `'off'` 会让"只有用户名 + 密码"的现存所有者在升级那一刻被挡在门外。这不是假想:`putSettings` 对 `passwordLogin` 没有任何守卫,而 `Bootstrap` 给首个所有者建的唯一标识符就是 username + password,所以这个自锁在改动前就存在——本次一并补上守卫:保存「关闭」时,调用者自己除密码外没有任何登录途径就返回 422,措辞对齐既有的「请先为自己开启两步验证」。
- 从此**无法表达「只有管理员能用密码、普通用户不能自己设密码」**。这个策略的正确形状是另一个开关(「允许用户自己设置密码」),而不是与"谁能用密码登录"合并。
- 一份别人知道的初始密码不再是唯一的进人途径,所以 ADR 0016 的邀请与初始密码是两条并列的路,初始密码受本开关约束。
- `00003_identity.sql` 的 CHECK 约束、`management/settings.go` 的 enum、`consoles.md` 的登录方式 Tab 交互与 `authentication.md` 的密码一节都要同步。
