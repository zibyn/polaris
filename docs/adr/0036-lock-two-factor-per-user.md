# 两步验证按 User 锁定

规格原来写的是两步验证"不按 User 锁定":每个待完成的登录最多错 5 次,其余交给单个 IP 每小时 50 次失败的限制。这挡不住换 IP 的攻击者:知道密码以后不断重新登录,每次登录又能错 5 次,一天下来大约有一半的概率猜中 6 位 TOTP。两步验证本来就是为"密码已经泄露"准备的,所以改为按 User 锁定。

- 锁定键 `2fa:<sub>`,沿用密码锁的失败计数和锁定机制。TOTP 和恢复码的错误合并计数,24 小时内连续错 10 次锁 15 分钟,输对一次清零。每次登录最多错 5 次的规则不变。
- 计数放在身份模块"检查第二因素"的唯一入口,托管页、直连 API、账号中心重新认证共用一个计数。先查 IP 锁,再查 User 锁;被 User 锁拒绝也计入 IP 失败。
- 锁定期间正确的码也拒绝。被锁不结束进行中的登录,`auth_session` 照样有效,锁过了可以接着输。
- 关闭两步验证(本人关闭或管理员重置)时,锁定和失败记录一并清除。
- 锁定时写 `login.two_factor_locked`,带 sub 和 `until`,和 `login.password_locked` 对称。

能走到这一步,说明攻击者已经知道密码;被锁的代价只是这个 User 15 分钟内不能用 TOTP 登录,Passkey 登录不经过这一步,不受影响。按 10 次一锁、每锁 15 分钟算,一天最多只能试约 960 次,猜中概率从约一半降到千分之几。这个代价换来的保护是值得的。

## Considered Options

- **维持不按 User 锁定,只收紧 IP 限制**:攻击者换 IP 的成本很低,收紧 IP 限制挡不住,反而误伤共用出口 IP 的正常用户。
- **锁定时结束进行中的登录**:攻击者本来就会重新登录,结束登录不增加他的成本,只让正常用户锁过以后还得从头再来。
- **阈值和密码锁一样定为 5 次**:每次登录本身就允许错 5 次,定为 5 次时,正常用户一次登录手滑几下就会被锁。5 次能让攻击者一天的尝试再少一半,可 10 次时的千分之几已经够低,不值得拿正常用户的体验去换。

## Consequences

- 知道密码的攻击者可以故意输错,让 User 15 分钟内不能用 TOTP 登录。这是有意接受的:User 仍可用 Passkey,或由管理员重置两步验证立即解除。
- 控制台没有手动解除锁定的入口,需要时用重置两步验证代替。
