# 管理员可以创建 User:待激活状态与邀请

User 原本只从登录中产生(登录即注册、Provider 登录、首次引导)。管理员现在也能创建:在 Management API 上进入「待激活」状态,只等本人设置密码后激活。创建时管理员代填的邮箱或手机号**直接算已验证**,不发验证邮件——与 GitLab 建号时替用户确认邮箱、Keycloak Add User 表单里的 Email Verified 勾选同形。邮箱或手机号填错,就是这个账号落进填错的那个值手里;代价与那两家一致,由管理员线下核对承担。

## Considered Options

- **每个新 User 发一封验证邮件**:渠道没配置时这条路直接走不通,而且"管理员建号"本身就不该要求本人先证明什么。
- **给待激活单独加一个布尔标志**(而不是 User 状态):用户列表要显示它、审计要记它、能力要按它限制,三处需要同一个概念,所以它值得是一个状态。
- **待激活期间也允许绑手机号、开两步验证**:会在"还没激活就开了两步验证、然后忘了临时密码"处打结,所以一律要求先激活。
- **邀请与重置密码链接做两套机制**:同一个 token 表、两种铸造入口(创建时发出、对已有 User 发出)代码更少,并顺手补上 `identity.md#找回` 里的缺口——忘记密码的 User 此前没有任何自救或被救路径。

## Consequences

- **待激活要能登录**,否则本人无法激活;但它拿不到 authorization code、拿不到任何令牌,所以 Application 侧看不到这个状态:不加 claim、不加 scope。直连 API 的 `next` 增加取值 `password`(ADR 0010 允许新增,不改名)。
- **强制改密必须是一条独立的密码写入通路**,不能复用账号中心的 `PUT /v1/account/password`:那条路要求近期重新认证,而重新认证对开了两步验证的 User 一律拒绝密码和验证码,2FA 用户会卡死。
- **这一条与不变式 1「至少一个可登录途径」的关系要写进 `identity.md`**:待激活的 User 有凭据但不能用,不变式依然成立。
- **待激活是已知的第三种 User 状态**,`users` 表原先只有 `disabled_at` 一个状态列。
- 管理员创建的 User 照常拿默认 Role(rbac.md 的「User 创建时授予」对所有创建途径一致)。
- **密码登录开关是这一包功能的前置条件**:`password_login` 为「关闭」时,`POST /users` 一律 422,管理端的创建入口禁用并说明原因。邀请和初始密码**都要走密码**,所以两者一起被挡——把开关关掉就是声明"这个实例不用密码",此刻再预置一个别人知道的密码没有意义。ADR 0017 把开关改成两档并默认开启,所以正常实例上这条功能开箱可用。
- **创建必须恰好给一个凭据来源**:初始密码,或一封邀请(邀请只支持邮箱,所以那种情况下邮箱必填)。不提供"只填标识符、等本人自己登录激活"的第三种方式——那样建出来的账号会被"登录即注册"照常认领,提前配权限的需求建完再配即可。
- 管理员代填的标识符算已验证,所以**能走验证码登录**——这一条是对外契约的一部分,写进 `identity.md` 与 `authentication.md`。
