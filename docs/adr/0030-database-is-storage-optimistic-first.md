# 数据库只做存储:不放触发器和业务规则,并发控制乐观优先

PostgreSQL 只负责存数据和守护数据完整性,业务规则一律写在 Go 和显式的查询里:

- **不用触发器。** 副作用由写操作自己做,和 ADR 0025(审计)、ADR 0026(Webhook)同一取向。
- **不用存储函数和视图承载业务规则。** 比如「Session 何时失效」「两步验证何时算满足」「事件 payload 长什么样」,这些规则写在 Go 里。需要按派生值查询时,由应用算好写成普通列(例如 Session 的失效时刻),不在查询时临时算函数。
- **业务常量不写进库。** 有效期、尝试次数、保留天数、密钥和 ID 的生成,都由 Go 作为参数传入,不用列默认值或 SQL 里的字面量。
- **约束保留。** NOT NULL、CHECK、外键、唯一约束属于存储层的职责:它们在并发下仍然成立,应用代码靠自己做不到。乐观并发本身就依赖它们。
- **并发控制乐观优先。** 单行冲突用条件更新(`UPDATE … WHERE` 写上读到的旧值或 version,影响 0 行即冲突),一次性凭证靠「删一次」或唯一约束。跨行不变式(实例至少剩一位所有者、User 至少剩一种登录方式)用 `SERIALIZABLE` 事务加冲突重试。

例外,只限以下场景,并在代码里写明原因:

- 高争用的计数限流(发码配额):乐观重试会让所有写入方一起失败、一起重来,保留 advisory lock,或改用条件自增的计数行。
- 队列领取(`FOR UPDATE SKIP LOCKED`):锁只在单条语句里持有,这是 PG 上标准的领取写法。
- 单条语句内需要读到并发写入之后的最新行、并把读到的旧值写到别处(刷新令牌宽限期轮换要记下被替换的 token):PG 15 的 `UPDATE … RETURNING` 拿不到旧值,只能在同一语句里 `FOR UPDATE`。锁不跨出这条语句。
- 迁移锁。

## Considered Options

- **维持现状:触发器、函数和锁按需使用。** 一条规则同时出现在 Go 和 SQL 两边;触发器的副作用在读代码时看不到(Back-Channel Logout 曾经靠 `sessions` 上的触发器入队,级联删除时也会触发);函数派生的值没法建索引,活跃 Session 的判断因此要全表扫。
- **连约束一起移出数据库,让数据库成为纯粹的 KV。** 唯一性和引用完整性在并发下只有数据库能保证,应用层的「先查后写」做不到;乐观并发也会失去冲突检测的手段。
- **全面悲观锁(`FOR UPDATE`、advisory lock、`LOCK TABLE`)。** 正确但会在应用逻辑执行期间一直持锁,争用和死锁风险都随副本数增长;而且防不住两个管理员先后编辑时的丢失更新,除非把读到的版本一路带回写入。

## Consequences

- 现存的触发器(`queue_logout_tokens_*`)、函数(`session_lapses_at`、`user_event`、`has_passkey`、`totp_confirmed`、`two_factor_satisfied`)、视图(`live_sessions`)、生成列(`users.pending`)和 SQL 里的业务常量,逐步迁出;新代码不再引入。
- 现存的 `FOR UPDATE`、advisory lock 和 `LOCK TABLE`,除上面列出的例外外,逐步改成条件更新或 `SERIALIZABLE` 事务。
- 一条语句里用 CTE 同时改数据、写审计、入队 Webhook 的写法保留:它是单条语句,天然原子,只是显式地写出了副作用,不算把规则藏进数据库。
- 副作用改成显式之后,漏写不会报错,所以每一类副作用都要有表驱动测试兜底,做法同 ADR 0025、ADR 0026。
