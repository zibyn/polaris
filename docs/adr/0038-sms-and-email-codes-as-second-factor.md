# 短信验证码和邮箱验证码可作为两步验证的第二因素

两步验证的第二因素原来只有 TOTP、Passkey 和恢复码(ADR 0037),没装验证器、也没有 Passkey 的 User 想挡住拿到密码的人,只能先去装一个。改为短信验证码、邮箱验证码也可以当第二因素,条件是 User 先把它们添加为第二因素。Polaris 的验证码本来就是第一因素(无密码登录),所以规定第二步不能与第一因素走同一渠道:同一渠道收两次码,证明的是同一个因素。参照 Logto(v1.32 起支持短信、邮箱 MFA)和 Auth0(支持短信、邮箱)。

- **添加**:User 在账号中心把已验证的手机号或邮箱添加为第二因素,只要求重新认证,不再发码确认:Identifier 本来就已验证,再收一次码证明的还是同一件事(同 Logto)。User 只有这一个渠道能登录(没有密码、没有 Provider、也没有另一种 Identifier)时拒绝添加:他每次登录第二步都只剩恢复码,得不到任何保护。这项检查只在添加时做,之后删密码、解绑别的登录途径不再检查;万一只剩同一渠道,第二步给恢复码,并提示改用别的方式登录。添加时提示风险:短信和邮件验证码比验证器、Passkey 更容易被截获,建议同时添加验证器或 Passkey。
- **开启**:只添加了短信或邮箱验证也能开启两步验证,照样生成 10 个恢复码。开着时再添加、移除这类因素不重新生成恢复码,与 TOTP 一样单独记审计。
- **渠道排除**:第一因素是短信验证码时,第二步不提供短信验证码;邮箱同理。第一因素是密码、Provider 时两种都提供。渠道按种类算,不按号码。
- **提供哪些**:第二步列出 User 已添加的全部因素,只去掉与第一因素同渠道的那种;有 TOTP 或 Passkey 时不隐藏短信码和邮箱码,添加是 User 自己的选择。
- **不受登录方式开关约束**:只要对应的 Channel 配置可用,第二步就能发码;实例关掉「短信验证码登录」不影响短信码当第二步。Channel 不可用时不提供这种方式,User 仍有其他因素和恢复码。
- **发码与输错**:发码沿用现有验证码按 Identifier、按 IP 的发送限制,与登录发码共用同一组计数;每个码最多试 5 次、5 分钟有效不变。输错计入 `2fa:<sub>`(ADR 0036),与 TOTP、恢复码合并计数,也占每次登录 5 次输错的机会:验证码能猜,和 Passkey 不同。账号中心重新认证同样接受这两种因素,共用同一个计数。
- **`amr`**:第二步用短信码为 `[第一因素, "sms", "mfa"]`,用邮箱码为 `[第一因素, "otp", "mfa"]`,与第一因素的取值一致,重复的不再加。「密码 + 邮箱码」与「密码 + TOTP」因此同为 `["pwd", "otp", "mfa"]`,接受分不出来:RFC 8176 没有邮箱的取值,自造的值接入方不认识。
- **直连 API**:`next` 新增 `sms`、`email`(User 只剩这一种时),`methods` 新增同样的取值。在同一 `auth_session` 上提交 `two_factor=sms` 或 `two_factor=email` 发码,返回已有的 `next: "code"`,再提交 `code` 完成第二步。进入这一步时不自动发码:User 可能选别的方式,也可能放弃,白发一条短信。老 SDK 遇到新的 `next` 按 `unsupported_step` 失败,`methods` 里的新取值被忽略(ADR 0010 只增不改)。
- **最后一个因素**:判断两步验证还剩什么时,TOTP、可用的 Passkey、短信、邮箱四种一起算。移除最后一个因素,或删除它所在的 Identifier,本人和管理员都返回 409,在 SERIALIZABLE 事务里检查(同 ADR 0037)。不是最后一个时,删除 Identifier 连带移除对应的因素并记审计。更换手机号或邮箱(新号码已验证)时因素跟着换过去,不用重新添加。
- **管理员必须启用两步验证或 Passkey**:只靠短信码或邮箱码开着两步验证也算满足,"满足要求"仍只看两步验证是否开着;开关说明里建议管理员使用验证器或 Passkey。

## Considered Options

- **有手机号、邮箱就自动可用,不必添加**:User 不知道自己的邮箱能当第二步;「最后一个因素不能删」也没有落点,解绑邮箱会悄悄改变两步验证的状态。
- **学 Logto,短信不能同时作登录方式和第二因素(实例级互斥)**:国内实例几乎都开着短信登录,这样等于没人能用短信做第二步;按单次登录排除同渠道就够了。Logto 担心的「短信重置密码再用短信过 MFA」在这里不成立:Polaris 没有重置密码流程,忘了密码只能用验证码登录,而那次登录照样要过第二步,同渠道又被排除。
- **添加时再发一次码确认**:Identifier 已经验证过,多一条短信、多一步操作,不多证明什么。
- **只在没有 TOTP 或 Passkey 时提供**:防降级,但 User 主动添加的因素被悄悄藏起来,丢了验证器时反而用不上。
- **管理员必须用 TOTP 或 Passkey**:要引入「强的两步验证」这个新概念,控制台、`twoFactorOrPasskey` 都要跟着改;换来的只是针对换卡攻击的额外保护,改成在开关说明里建议。
- **第二步单独计发码频率**:等于把能发的短信翻倍。

## Consequences

- 短信码、邮箱码比 TOTP 更容易被截获(换卡、邮箱被盗),只用它们开着两步验证的 User,保护比用验证器的弱;这是有意接受的,界面上提示风险。
- `amr` 不能区分邮箱码和 TOTP;需要区分的接入方做不到。
- 只能用手机号登录的 User 不能用短信做第二步,要先设密码或绑邮箱。
- 第二步可能要发短信,计入实例每日发送上限;攻击者知道密码后可以反复触发发码,受按 Identifier 每小时 5 条、每天 10 条的限制。
- KMP SDK 要支持新的 `next` 取值和发码;老版本 App 遇到只有短信或邮箱的 User 会提示升级。
