# 经 Management API 建正常 User 与导入密码哈希

`POST /users` 新增一种建号方式:只带 Identifier,可选附带集成方原有的密码哈希,建出来就是正常 User,不进待激活。这放宽了 ADR 0016「创建必须恰好给一个凭据来源」:待激活只留给「管理员替人定了一个别人知道的密码」(初始密码或邀请)。代填的手机号、邮箱照 ADR 0016 算已验证,由调用方担保。哈希只收 argon2id(PHC 字符串)与 bcrypt(`$2a$`/`$2b$`/`$2y$`),User 首次凭它登录成功后转存为 argon2id。导入就是逐个调用 `POST /users`,不另设批量接口。

## Considered Options

- **惰性迁移**(Polaris 验证不了时回调集成方端点代验密码,Auth0、Cognito 有):Polaris 的登录要依赖集成方在线,方向与「集成方后台调 Polaris」相反。
- **只能建待激活 User**(维持 ADR 0016):老用户每人都得被迫改一次密码;ADR 0016 担心的「被登录即注册认领」不成立,因为能用验证码认领该 Identifier 的就是它的主人。
- **批量接口**:要额外定义部分失败、事务边界与限流;逐个调用几万用户也只要几分钟。
- **收 PBKDF2、scrypt、salted SHA/MD5 等更多格式**:弱哈希等于把弱口令库原样搬进来;其余格式等有需求再加。
- **`external_id` 关联集成方旧主键**:违背 ADR 0032;`POST /users` 返回 `sub`,集成方自存。

## Consequences

- Identifier 冲突返回 409,body 带已有 User 的 `sub`(ADR 0031 下调用方本就看得到整个用户池),整个请求失败、不部分写入;集成方据此直接关联已在 Polaris 登录过的人。
- `password_login` 关闭时,只有带初始密码、邀请或哈希的请求 422;只带 Identifier 的照常允许,否则只用验证码的实例导入不了老用户。
- 只有用户名 + 哈希的 User 可以导入,导入的密码就是它的登录途径,满足不变式「至少一个可登录途径」;哈希格式不支持时整个请求 422。
- 待激活 User 能用验证码登录,但先要设自己的密码才拿得到令牌(ADR 0016 不变)。
