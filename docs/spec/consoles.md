# 管理端与账号中心

两者都内嵌在二进制中,技术栈为 TanStack + shadcn/ui(Base UI 原语)。管理端是内置的 First-party Application,经 OIDC 登录,数据全部来自 Management API。只做中文界面,不引入 i18n 框架;界面上每个概念叫什么,以下文的[界面用语对照表](#界面用语对照表)为准。

## 管理端

### 读者

- **应用、API 资源、认证源、设置**四组面向开发者:可以保留 `client_id`、回调地址等必要术语,每个都配一句人话说明。
- **用户、审计**两组面向运营和客服:不出现协议词汇。

### 导航

七个分组,依次为:

| 分组 | 页面与层级 | 所需 Permission |
|---|---|---|
| **概览** | 统计数字、最近事件、上手清单(见[概览](#概览))。 | `users:read` |
| **用户** | 列表 → 用户详情页。 | `users:read` |
| **应用** | 列表 → 创建页 → 应用详情页。 | `applications:read` |
| **API 资源** | 列表 → API 资源详情页。 | `applications:read` |
| **审计** | 单页列表加筛选,不设事件详情页。 | `audit:read` |
| **认证源** | 列表 → 选类型页 → 编辑页(即详情页)。 | `config:read` |
| **设置** | 单页三个分类:登录方式、验证码通道、安全。 | `config:read` |

- **详情一律是独立页**,可以链接;**创建、添加、编辑某个对象的小表单用右侧抽屉**,列表或详情页留在背后不跳走。多步创建(创建应用、添加认证源)仍是独立页。
- **按钮可见性**:缺少相应 Permission 的操作按钮不显示。
- **密钥字段**:只写不回显,只显示"已设置 · 更新于 X",只能整体替换。
- **Tab**:页面里的 Tab 一律用 shadcn Tabs(`variant="line"`,不另加样式),当前 Tab 放在 `?tab=`,不带参数即默认 Tab。设置页的分类导航例外,见[设置](#设置)。
- **保存**:设置组按分区保存,前端把同一资源里没改的值原样带回,Management API 不变。

### 页面

#### 概览

- **统计**:用户、今日新登录(悬浮说明"今天新建的会话数")、活跃会话、应用(只计非内置,前端按 `builtin` 过滤)。
- **最近事件**:与审计页用同一张表。
- **上手清单**:三步,依次为 配置通道 → 创建应用 → 添加 API 资源。完成状态由 `GET /channels` 和应用、API 资源列表的 `builtin` 推出;看不到的步骤不显示;全部完成后自动隐藏,也可以手动关掉。它是一次性的上手引导,不做持续的配置健康检查。
- 每日发送上限的告警条保留不变。

#### 用户

- **列表**:搜索手机号、邮箱、用户名或用户 ID;角色列;按角色与状态(全部 / 已激活 / 待激活)筛选;工具栏有「创建用户」。
- **创建用户**是独立页,两项:登录标识,与**怎么把账号交给本人**(「设初始密码」/「发注册邀请」,默认前者)。标识符可以是手机号、邮箱或用户名,选邀请时必须是邮箱——邀请只发邮箱。管理员填的邮箱或手机号**直接算已验证**,不发验证邮件、不消耗验证码条数。初始密码由管理员当面或另找渠道交给本人,本人第一次登录时必须改掉;邀请是一条 7 天有效的一次性链接,密码只经过本人。成功后进入新用户的详情页;邀请邮件发不出去时账号**已经建好**,页面上就说明这一点并让人去用户页重发——不然管理员会当它没建成再点一次,那次撞的是「这个邮箱已属于另一个 User」。密码登录关闭时入口禁用并说明原因(见[依赖提示](#依赖提示))。
- **待激活**的账号(管理员建出来、本人还没设置自己的密码)在列表和详情都标出来,状态筛选里与「已激活」相对;这个状态本身见 [identity.md](identity.md#待激活与激活)。
- **用户详情**是一页长滚动:
  1. **头部**:主登录标识、状态(已激活 / 待激活 / 已禁用)、禁用 / 删除操作,不显示用户 ID。待激活的账号在状态下面加一句说明:本人设置自己的密码之前拿不到任何令牌。
  2. **登录标识与密码**:手机号、邮箱、用户名(可更换)与密码状态。
  3. **注册邀请**:未发出 / 已发出(写明什么时候过期)/ 已接受。持有 `users:write` 的管理员可以发出、重发、撤销(对方是管理员时还需要 `admin-roles:assign`,和禁用、删除管理员一致),都先弹确认框(正文写后果:重发让旧链接立刻失效,撤销后本人得找管理员重发)。发出的去向是账号上的邮箱;没有邮箱的账号不给按钮,只显示状态和一句说明。只读角色只看到状态。
  4. **已绑定的外部账号**:列出本用户绑定的认证源(解绑规则见[认证源](#认证源))。
  5. **两步验证**:已开启 / 由 Passkey 满足(没开两步验证但有 Passkey)/ 未开启。已开启时,持有 `users:write` 的管理员看到「重置两步验证」按钮(对方是管理员时还需要 `admin-roles:assign`,和禁用、删除管理员一致),先弹确认框(提醒先线下核实身份;清除验证器和全部恢复码,已登录的设备不下线)。只读角色只看到状态。
  6. **Passkey**:每把显示名称、创建时间和最后使用时间(尚未使用就写"尚未使用");没有 Passkey 时显示空状态。持有 `users:write` 的管理员可以删除某一把(对方是管理员时还需要 `admin-roles:assign`,和禁用、删除管理员一致),先弹确认框;删除写审计,操作人是管理员本人,和用户自己删除区分开。只读角色只看不能删。「重置两步验证」不动这里的任何一把。
  7. **会话**:可以下线,也可以一次下线全部会话。
  8. **角色**:按 API 资源分组,是**唯一**给 User 分配角色的地方。
  9. **更多信息**(折叠):用户 ID 等。
- 详情页上有「查看审计记录」链接,跳到按该用户筛选的审计页。

#### 应用

- **创建**见[创建应用与接入清单](#创建应用与接入清单)。
- **应用详情**分三个标签;后端服务没有「登录」(它不登入任何 User),换成「角色」:
  - **基本**:名称、类型(只读;「无后端应用 / 有后端应用 / 后端服务」,写明各适合什么、创建后不能改)、`client_id`、client secret、默认 API 资源(链到对应的 API 资源详情)、「要求用户有角色」开关(让 User 登录的应用;没选默认 API 资源时置灰并说明原因,见 [rbac.md](rbac.md#签发时检查-role));页面底部是红框删除区。后端服务的默认 API 资源只读:它换到的令牌只对这个 API 有效,创建后不能改。
  - **登录**:回调地址;「高级」折叠区里放退出后跳转地址、「闲置多久需重新登录」、「允许 App 保持登录」。无后端应用多一组「原生 App 关联」:iOS 的 Team ID + Bundle ID、Android 的包名 + SHA-256 签名指纹,各按行登记在文本框里,可以增删;保存后认证服务据此生成 `/.well-known/` 关联文件(见 [authentication.md](authentication.md#密码管理器适配)),iOS 和 Android 就允许这些 App 使用这个域名的通行密钥和密码自动填充。有后端应用不显示这一组,改为一组「退出通知」:一个 Back-Channel Logout 通知地址(`backchannel_logout_uri`),留空即不发(见 [protocol.md](protocol.md#back-channel-logout))。后端服务不登录,没有这个标签。
  - **角色**(后端服务):勾选它在其默认 API 资源上持有的 Role,它换到的 access token 带上这些角色与权限(见 [rbac.md](rbac.md))。默认 API 资源是管理 API 时,需要 `admin-roles:assign`;该 API 资源还没有角色时,链到 API 资源详情去建。
  - **用户删除通知**:通知地址与 Webhook 密钥,有一句导语说明用途。
- 样页(应用详情的全部改写文案)见原型 [`prototype/console-copy`](https://github.com/zibyn/polaris/blob/prototype/console-copy/prototypes/console-copy/index.html) 的 A 版,以其 `NEW` 对象为准;删除区用 C 版的红框独立区块。

#### API 资源

- **API 资源详情**有「权限」「角色」两个标签。
- 添加 API 资源、添加权限、添加 / 编辑角色都用右侧抽屉,列表与详情留在背后。
- 角色行显示持有人数(含持有它的 M2M Application);点击跳到按该角色筛选的用户列表。
- 业务 API 资源的角色行有「默认」勾选,勾上后新 User 创建时自动获得该 Role(见 [rbac.md](rbac.md));只读角色看到的是「默认」徽章。内置 API 资源上不出现。
- 显示"被哪些应用用作默认 API 资源",并链到这些应用。
- API 卡片上原来那句"只带当前 aud 那个 API 的 roles 和 entitlements",改为人话。

#### 审计

见[审计](#审计-1)。

#### 认证源

导航里叫「认证源」,排在「设置」前面:两者都在回答"用户怎么登录",但认证源是对象集合(多个实例,各有不可改字段、回调 URL、已绑定人数),设置是实例开关。

- **列表**:已添加的认证源,显示名称、类型、Provider ID、启用状态、已绑定人数;行内操作 编辑 / 停用·启用 / 删除。
- **添加**先进入选类型页,给一张类型目录,选完进入表单;编辑页就是详情页。
- **类型目录**(类型由代码注册、随二进制发布,ADR 0004):
  - **Google**、**Microsoft**、**GitHub**:常见供应商,开箱可用;端点、scope 与品牌写死在类型里,表单只问 client_id 与 client secret。
  - **通用 OIDC**:自填 issuer(必须提供 discovery)、client_id、client secret;issuer 创建后不可改。
  - **通用 OAuth2**:自填 authorization、token、userinfo 三个 endpoint、scope,以及 **userinfo 里哪个字段是用户 ID**;不校验 id_token,身份不带上游签名背书(ADR 0013)。这个字段必须选上游不会变的(如 GitHub 的数字 `id`,而不是随时可改的 `login`)。
  - **Apple**:Team ID、Key ID、`.p8` 私钥、Services ID、Bundle ID。
- 具名供应商与两个通用类型**共用同一份实现**,差别只在端点、scope、品牌是否预填。
- **Microsoft 比其他供应商多一个字段**:不可改的租户,填 `common`、`organizations` 或具体租户 ID;前两者接受任意 `https://login.microsoftonline.com/<租户 GUID>/v2.0` 的 issuer,其余值严格校验(ADR 0013)。
- **Provider ID** 只在添加时填,之后不可改,出现在回调 URL 与直连认证 API 里;issuer(通用 OIDC)、租户(Microsoft)同理。回调 URL 显示在表单里,可以复制。
- **停用**的确认弹窗写明"N 个用户已绑定,其中 M 个没有其他登录方式,停用后他们无法登录"。还有绑定的认证源不显示删除按钮。
- 用户详情的「已绑定的外部账号」分区列出认证源名称和绑定时间;持有 `users:write` 的管理员可以解绑,受"最后一个登录途径"约束。

#### 设置

三个分类,依次为登录方式(默认)、验证码通道、安全,`?tab=` 取值 `login` / `channels` / `security`。分类导航是页面内左侧的竖排列表(每项下方一句说明它管什么),窄屏收成横向一排;它不是页面 Tab,也不进面包屑。切走分类时未保存的输入会丢,不做离开提醒。

- **登录方式**:开放注册、密码登录、Passkey、必须绑定手机号、用户协议(两个 URL 加版本号)、两步验证("管理员必须启用两步验证或 Passkey"开关),每个分区单独保存。自己既没开两步验证也没有 Passkey 时保存"打开",后端拒绝,分区内显示 Alert「请先为自己开启两步验证」。密码登录是「允许密码登录」开关,只有开与关两档;关它时若自己除密码外没有别的登录途径,后端同样拒绝。开放注册是一个开关,默认打开,关闭后的行为见 [identity.md](identity.md#不变式) 不变式 2。

Passkey 开关默认打开,关它时若自己只剩 Passkey(既没开两步验证)同样被拒绝,同一个 Alert。关闭后所有 Passkey 入口都消失(登录页、账号中心、`/.well-known/passkey-endpoints`),ceremony 一律拒绝,已添加的 Passkey 保留,重新打开即恢复可用;关闭期间 Passkey 也不再满足"管理员必须启用两步验证或 Passkey",只剩 Passkey 的管理员会被拦在管理端外。`/.well-known/` 的两个关联文件还服务密码管理器的自动填充,不受开关影响。

开关打开后,既没开两步验证也没有 Passkey 的管理员进入管理端(或已经登录着、下一次调用 API)时,整个管理端换成**拦截页**:写明「需要先开启两步验证或添加 Passkey」,按钮「去账号中心」。前端凭错误码 `two_factor_required` 识别,不靠文案。账号中心本身不受开关影响。
- **通道**:短信、邮件、每日发送上限。每个分区顶部写清没开启的后果(如"没开启时,用户不能用手机号收验证码登录"),下面是启用开关和表单;不另做空状态。
- **安全**:令牌签名密钥(列表与轮换)、审计保留期。

#### 协议字段(只出现在开发者组)

- **原文加一句说明**:`client_id`、client secret、Webhook;access token 只出现在说明文字里。
- **中文名,说明里附原文**:回调地址(redirect URI)、退出后跳转地址(post-logout redirect URI)。
- **按行为命名**:"签发 refresh token" → 「允许 App 保持登录」,说明"签发 refresh token,每次刷新都给会话续期"。
- **sub** → 「用户 ID」,只出现在用户详情的"更多信息"里和审计筛选中。
- **不上界面**:`aud`(只在标识符说明里)、scope、entitlements、roles claim。

#### 撞名消解

- 用户详情的分区叫「登录标识与密码」;「登录方式」只用作设置组的一个分类名。
- 设置组里的叫「令牌签名密钥」;应用里的叫「Webhook 密钥」。
- 「认证源」指外部身份提供者;通道背后的短信、邮件厂商仍叫「供应商」,两者不混用。

### 文案风格指南

1. **标题与标签**:中文名词短语,不带单位括号,单位放进输入框后缀(「Session 闲置寿命(天)」→「闲置多久需重新登录」+ 后缀「天」)。保留原文的技术字段,整个标签就用原文(`client_id`),不和中文拼成混排标题;需要时在标签旁用小字附原文(「回调地址 redirect URI」)。
2. **帮助文字**:放在字段下方,写一到两句完整的话:先说作用或为什么要配,再说不配 / 关闭的后果。不用分号串规格;不言自明的字段(如名称)不写帮助。
3. **格式与默认值**:放进占位符或输入框后缀,不写进帮助文字。
4. **占位符**:只放示例或默认值;输入后就看不见了,所以不放必须看到的说明。
5. **错误提示**:先说怎么做,再说原因。例:「请设置 Webhook 密钥。填写通知地址后,必须同时设置密钥。」
6. **确认框**:用对话框,不用浏览器原生的 `confirm()`。标题是带对象名的问句,正文说后果(谁受影响、能否撤销),确认按钮写 动词 + 对象(「删除应用」「重新生成」),不写「确定」。删除类操作放在页面底部的红框独立区块里,先说明后果,再给按钮。
7. **语气与称呼**:称读者为**你**;产品在文案里自称**认证服务**,品牌只出现在导航外壳和登录页(见[视觉规范](#视觉规范))。用全角中文标点,中英文之间留空格。
8. **分区**:分区标题按"这组设置管什么"来命名(基本信息、访问令牌、登录跳转、用户删除通知);只有一句帮助说不清"为什么"时,分区才加一句导语(如用户删除通知)。

### 视觉规范

管理端、账号中心和登录页共用一套视觉语言:Polaris 品牌,取北极星之意,配色名「星云」。Polaris 是各 Application 共用的身份底座,这套规范也是以后界面的起点。原型(一次性)见分支 `prototype/console-style`,三轮依次为整体风格、品牌表达、配色,选中的是方案 D。本次只做浅色。

**一体感来自一致,而不是装饰。**下面每一条都是能逐页检查的规则。

#### 配色

颜色只从下表取,写成 `styles.css` 里的 token(映射到 shadcn 的 `--primary`、`--muted` 等),页面里不写死色值。

| Token | 色值 | 用途 |
|---|---|---|

#### 外壳与分组

- **外壳**:画布底色,左侧导航(星标 + 「Polaris / Auth」字样,下列七个分组,底部是当前管理员),右侧是**一整块**白色面板:圆角 16px,1px 分隔线描边,极淡阴影。导航顶部的产品字样为以后切换其他产品留位置,现在不可点。
- **页头**:每个页面都用同一个页头,依次为:
  1. **面包屑**:在面板顶部,13px 次要色,每页都有,只到页面这一级,不含 Tab。列表页只有一级(「应用」),详情页两级(「应用 / 订单 App」),最后一级是当前页、不可点。由路由的 `staticData.crumb` 给出,布局路由收集后渲染。
  2. **标题行**:与面包屑相隔 24px。标题 24px 半粗,后接徽章(类型、内置、状态),操作按钮靠右。
  3. **说明**:可选,一句话讲这页管什么;规则同分区导语,只在需要讲"为什么"时写。
  4. 页面特有的提示(只读说明、接入清单),最后是 Tab 栏。
- **面板里不再套卡片。**分区靠「分区标题 + 留白」分开,分区之间留 40px;同一分区内的条目用分隔线隔开。现有的 `Card` 用法(概览统计、`Section` 表单、最近事件等)全部改为这种分区。
- 统计数字排成一行,用竖分隔线隔开,不做成四张卡片。
- 只有三种块可以有底色或边框:**强调块**(上手清单、告警条)用浅底、无边框;**危险区**保留红框(见文案风格指南第 6 条);**空状态**保留虚线框。
- 不用 emoji、渐变和插画。图标只用 lucide。例外只有两处:登录页品牌区的星云渐变(见[登录页](#登录页));登录页上具名供应商(Apple、Google、Microsoft、GitHub)的按钮,按各自的品牌规范用官方标志和规定样式。通用 OIDC、通用 OAuth2 的按钮仍是纯文字。

#### 尺寸

- **圆角**:面板 16px,块 12px,按钮、输入框、导航项 8px,头像、状态点为圆形。
- **间距**:只用 4 / 8 / 12 / 16 / 24 / 32 / 40 / 56 px 这几档。面板内边距为左右 56px、上下 44px(窄屏依次收窄到 32 / 24px);页面内容铺满面板宽度;列表和统计用满,表单字段最宽 672px,长文可在页面内自限宽度。
- **字号**:页面标题 24px 半粗;分区标题 15px 半粗;正文 14px;标签、辅助文字 13px;时间、计数 12px;统计数字 30px 半粗,等宽数字。字体为 Inter 加系统中文字体。

#### 动效

- 状态变化用短过渡,不让元素瞬变:按钮按压与配色 100–150ms,输入框描边 150ms,焦点环渐显。过渡只覆盖颜色、阴影和位移,不改宽高。
- 页面进场只做一次:表单上浮 8px,登录页的星云光晕落定。除此之外装饰不持续运动;持续转动的只有加载指示。
- 尊重 `prefers-reduced-motion`:去掉进场动画和过渡,加载指示保留。
- 表单提交后按钮进入等待态(转圈),慢网络和 PoW 求解都有反馈;`altcha-widget` 自带进度,不再叠加。六位验证码填满即自动提交。

#### 登录页

登录、绑定、协议同意、首次引导、退出登录、**邀请接受页**(`/invite`,设完密码当场登录,再回到 Application 就不用登了)等页面(`internal/login/pages.html`)用同一套 token。

- 宽屏左右两栏:左半是品牌区,右半是表单,最宽 340px。窄屏只留表单。
- 品牌区是「星云」:主色浅底上叠两团径向渐变光晕(星云色、星标色),撒星标色星点和几颗四角星,左上角是星标和「Polaris」。原型(一次性)见分支 `prototype/login-layout`,选中的是方案 D。
- 表单区以 Application 为主角:标题「登录」,下一行「继续前往 <Application 名>」。Polaris 只出现在星标和底部的「由 Polaris 提供安全登录」。
- 「是否对外宣传统一的 Polaris 账号」尚未决定,所以品牌区**不写**口号,只放标志、星云和星点。
- **先输标识**:任何时候页面上只有一套表单。
  1. 第一步只有一个标识输入框、协议勾选和「继续」,下面是「使用密码登录」链接。
  2. 手机号或邮箱:「继续」时才运行 PoW,发码后进入填码页。用户名:不发码、不运行 PoW,直接进入密码步骤。
  3. 填码页和密码步骤顶部显示标识和「更换账号」(回到第一步);协议勾选只在第一步出现,之后用隐藏字段带上。填码页的「重新获取」直接向同一个标识重发,不再做人机验证;距上次发送不足 60 秒时按钮不可点,与按标识符的发送限制一致。
  4. 「使用密码登录」切到「标识 + 密码 + 协议勾选」的表单,其中有「改用验证码登录」。
  5. 密码登录设为关闭时不显示「使用密码登录」,输入用户名提示「该账号不能用验证码登录」,不透露账号是否存在。
  6. 只有一种方式可用时直接显示那一种:没有通道就只有密码表单。
  7. **邀请接受页是特例**:它是从邮件点进来的,没有 Application 可指,所以标题就是「设置密码」,只说明"点开这个链接就说明这个邮箱是你的",一个密码框加一个「设置并继续」。设完密码只在没有别的步骤剩下时才当场登录(见 authentication.md 的注册邀请);链接不好用(过期 / 用过 / 已撤销)时给一句人话并指向管理员,不复用发码失败那套文案。
- 所有密码框右侧带「显示」切换,点开后改为「隐藏」;只改输入框的可见性,不动输入内容、autocomplete 和校验。

### 创建应用与接入清单

原型见 [`prototype/app-create`](https://github.com/zibyn/polaris/blob/prototype/app-create/prototypes/app-create/index.html):创建页取 A 版,接入清单取 C 版。

**创建**

1. 在「应用」列表点「创建应用」,进入独立页面,问"你的用户在哪里登录?",给五张平台卡片,卡片下注明对应的类型:

   | 卡片 | 类型 | 回调地址 |
   |---|---|---|
   | 手机 App | 无后端应用(public) | 不需要(走直连认证 API) |
   | 小程序 | 无后端应用(public) | 不需要(走直连认证 API) |
   | 纯前端网页 | 无后端应用(public) | 必填 |
   | 有后端的网站 | 有后端应用(confidential) | 必填 |
   | 后端服务(M2M) | 后端服务(m2m) | 不需要 |

2. 第二页只填**名称**,网页类再加**回调地址**(必填),后端服务再选**默认 API 资源**(必填)。页首注明类型和"创建后不能更改",可以返回换平台。
3. 其余字段(退出后跳转地址、闲置多久需重新登录、允许 App 保持登录、用户删除通知)创建时都不问,留到应用详情里填。
4. 平台只用于引导,不入库;创建请求仍是 `{type, settings}`,Management API 不改。

**接入清单**

创建成功后直接进入应用详情,顶部显示「接入清单」,可以收起。清单由创建跳转时 URL 带的平台参数(如 `?onboarding=spa`)渲染,只显示这一次;之后从列表再进详情就不显示了。各项根据应用数据自动打勾:

1. 记下 `client_id`(自动完成,带复制按钮)。
2. 保存 client secret(无后端应用以外的都有):只显示这一次,勾选「我已保存」之前不能离开页面。
3. 选择默认 API 资源(可以跳过;帮助文字说明不调用自己的 API 就可以不选。后端服务的默认 API 创建时就选定了,这一步自动完成)。
4. 接入代码,按平台给出片段:手机 App 用 KMP SDK;小程序指向直连认证 API 文档;纯前端网页用 oidc-client-ts;有后端的网站用后端语言的 OIDC 库(issuer、`client_id`、client secret);后端服务用 `client_credentials` 换令牌的示例。另外列出认证服务地址。

清单末尾有两句提示,链到别处:去设置「登录方式」分类检查登录方式;需要在用户注销时清理数据,就配置「用户删除通知」。

### 依赖提示

**分工规则**:

- 后端已经拦截的 → 前端保存前先校验,措辞先说怎么做;
- 会让用户登不进、收不到验证码的组合 → 内联警告加跳转链接,不禁用;
- 必然失败或必然有害的操作 → 禁用,并说明原因;
- 执行时才造成后果的操作 → 确认框写明后果;

### 审计

**行**:三列,依次为 时间、操作人、事件描述。事件描述是一句话,句中的对象可以点击(用户 → 用户详情,应用 → 应用详情),例如「禁用了用户 138****0001」「把用户 a@x.com 在 订单 API 上的角色设为 编辑、只读」。概览页的「最近事件」用同样的一句话,排成分隔线列表(见[视觉规范](#视觉规范))。

**操作人**:显示主登录标识,数据来自 `GET /audit` 的 `user` / `byUser` 字段。缺省规则如下:

- 没有 `by` → 「系统」;
- `detail.byType` 为 `application` → 应用名称(数据来自 `/applications`);应用已删除或读者没有 `applications:read` → 等宽的原 client_id;没有 `byType` 的老记录按 User 解析;
- `by` 等于 `sub` → 「用户本人」;
- 用户已删除 → 「已删除的用户」加 ID 前 8 位(等宽字体)。

| 设置 | keys.rotated | 轮换令牌签名密钥 |
| 安全 | login.succeeded / failed | 登录成功 / 登录失败(句中写明方式和 Application,如「用验证码登录了 <Application>」「登录 <Application> 失败:密码错误」;IP 和 UA 放在悬停里) |
| | login.password_locked | 密码输错次数过多,暂时锁定(有 `until` 时写明锁定到几点) |
| | login.ip_locked | 同一 IP 登录失败过多,暂时锁定 |
| | refresh_token.reused | 疑似登录凭据被盗用,已下线会话 |
| | passkey.counter_regressed | Passkey 计数器回退,拒绝登录 |

没收录的事件显示「其他操作(<事件原名>)」,保证可以追查。

**筛选**:搜索框接受手机号、邮箱、用户名或用户 ID(占位符就这么写)。前端先用 `GET /users?q=` 解析出 `sub` 再筛;匹配到多个时给出列表让人挑;已删除的用户只能按用户 ID 查。

**详情字段**:

- `clientId`、API 资源标识符、角色 key:前端用 `/applications`、`/apis` 映射成名称;对象已删除,或读者没有 `applications:read` 时,退回等宽的原 ID。
- `by`、`byType` 决定操作人怎么显示(见上);`application_roles.assigned` 的 `clientId`、`api`、`roles` 写进句子,和 `roles.assigned` 一样。
- `kind` 映射为 手机号 / 邮箱 / 用户名;`limit` 写进句子(「每日上限 N 条」);`ip` 原样写进句子。
- `session`(会话 ID)不显示;Webhook 的 `id`(投递 ID)只放在悬浮提示里。
- Provider ID(`id`、`provider`)显示为等宽的原 ID;吊销失败的 `error` 只放在悬浮提示里。
- `settings.updated` 不记录改了什么,句子只写「修改了登录设置」。

### 空状态

- 管理员本身就是用户(ADR 0006),所以用户列表、会话、审计总有数据,不存在真正的空。
- **应用、API 资源列表"只剩内置项"就算空**:列表上方放引导块,内置项照常列出,标「内置」。出现第一个非内置对象时引导块消失,不能手动关闭。
- **三种引导各管一件事**:概览上手清单管跨页面的先后顺序;接入清单只管刚创建的那一个应用怎么接上;空状态只讲本页对象是什么、为什么需要,给一个入口,不复述步骤。缺少前置条件的,归[依赖提示](#依赖提示)。
- **格式**:标题加一两句说明(先说为什么)加主按钮(动词 + 对象),不配插画。只读角色看不到按钮时,写一句"需要「…」角色才能创建"。
- **筛选 / 搜索无结果**和真正为空分开写:"没有符合条件的…"加「清除筛选」,不放创建入口。适用于用户列表、审计、角色筛选。

| 位置 | 触发 | 标题 | 说明 | 按钮 |
|---|---|---|---|---|
| 应用列表 | 只剩内置 | 还没有接入你的应用 | 你的 App、网站或小程序要先在这里创建,才能让用户用认证服务登录。 | 创建应用 |
| API 资源列表 | 只剩内置 | 还没有你自己的 API 资源 | 如果你的后端要校验用户能做什么,在这里登记它,再定义权限和角色。只用登录、不需要权限控制的话,可以不建。 | 添加 API 资源 |
| 认证源列表 | 0 条 | 还没有添加认证源 | 加上 Google、GitHub 这些认证源,用户就能用它们登录;不加的话,用户只能用密码或验证码。 | 添加认证源 |
| API 资源详情・权限 | 0 条 | 还没有权限 | 权限是你的后端检查的最小单位,比如"导出订单"。先定义权限,再把它们组合成角色。 | 添加权限 |
| API 资源详情・角色 | 0 条 | 还没有角色 | 角色是一组权限,分给用户后,他们登录拿到的令牌里就带着这些权限。 | 添加角色 |
| 用户列表 | 只有管理员 | 还没有用户注册 | 用户在你的应用里第一次登录时会自动注册,之后出现在这里;你也可以直接建一个。 | 创建用户 |
| 用户详情・角色 | 0 条 | 没有角色 | 这个用户目前只能登录,不带任何权限。 | 分配角色 |
| 用户详情・会话 | 0 条 | 没有登录中的设备 | 这个用户目前在任何设备上都没有保持登录。 | 无 |
| 用户详情・Passkey | 0 条 | 没有 Passkey | 这个用户还没有添加过 Passkey。 | 无 |
| 概览・最近事件 | 0 条 | 最近没有事件 | 超过审计保留期的记录已经删除。 | 无 |

- 用户详情的角色区:没有可分配的角色(只剩管理 API 的内置角色)时,在按钮旁链到「API 资源」去建角色。
- **"只有管理员"的判断**:不加筛选(搜索、角色、状态都不设)的 `GET /users` 第一页 `hasMore` 为 false,并且每个用户的 `roles` 都含管理 API 上的角色。一条都没有也算。

## 账号中心:单页长滚动

原型(一次性)见分支 `prototype/console-ui` 的方案 A。

面向 User,桌面和手机共用一个页面,外观按[视觉规范](#视觉规范):画布上居中一整块白色面板,不设侧栏。从上到下依次是:

1. **头部**:头像和主标识。
2. **登录方式**:手机号、邮箱(更换、解绑)、外部身份(解除绑定;"绑定其他账号"只列出管理员启用的 Provider)。
3. **安全**:密码(开关允许时显示)、Passkey(实例开关允许时显示)、两步验证(开关与恢复码)。
4. **设备与会话**:每个 Session 的设备、IP、最近活动,可以下线;也可以一次下线其他设备(本设备保留);已结束的 Session 显示 30 天。
5. **最近登录**:本人 30 天内的登录成功、失败和密码锁定(取自审计日志的 `login.succeeded`、`login.failed`、`login.password_locked`),倒序混排,最多 50 条,不分页,查看不要求重新认证。每行显示时间、结果、方式、Application(取不到名称时退回 `client_id`)、设备和 IP;成功的方式是第一因素,经过两步验证的追加「+ 两步验证」,失败的方式是出错的那一步(如「密码错误」),锁定显示锁到什么时候。30 天内有失败时顶部写「过去 30 天有 N 次登录失败」,N 不受 50 条上限影响、不含锁定;底部提示修改密码并下线其他设备,不提供逐行操作。
6. **数据与隐私**:导出我的数据(JSON)。
7. **危险操作**:注销账号(重新认证,并输入"注销"确认)。

安全分区的 Passkey:每把显示名称(默认按提供方命名,如"1Password";查不到叫"Passkey")、创建时间和最后使用时间,可重命名(不要求重新认证)和删除(要求)。添加和删除都要求近期重新认证,都写审计;浏览器不支持 WebAuthn 时分区仍在,只是没有「添加」按钮。实例的 Passkey 开关关闭时整个分区(含重新认证时选 Passkey 的路子)都不出现,已添加的 Passkey 保留,重新打开即回到列表。`/.well-known/passkey-endpoints` 把密码管理器指到这里的锚点(`#passkeys`)。

所有敏感操作都在弹窗里先完成近期重新认证,规则见 [identity.md](identity.md#换绑与解绑)。
